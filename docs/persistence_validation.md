# 持久化校验记录

本次构建没有仅凭“程序返回完成”认定交付成功。

首次完整矩阵运行生成了结果，但关闭后重新检查时发现 8 个 repair.sqlite 存在索引或页面完整性问题。逐个复跑和跨运行文件哈希比对发现：单次即时检查可以通过，但连续矩阵过程中，已完成数据库的字节可能变化，并观察到遗留回滚日志。尚不能把根因确定归到某个 SQLite 版本或操作系统。

曾测试把回滚日志从 DELETE 改成 TRUNCATE：一个 144 次复现矩阵通过，但另一轮演示仍失败，因此该尝试没有作为交付修正。

最终采用“内存 SQLite 事务 + 带校验的文本检查点 + 结束时 SQLite 导出”。每次预算预留、事件提交、结束状态变更后，将 SQLite 完整镜像编码为带 SHA-256 校验的 JSON，保存在 .checkpoints/ 的递增编号文件中，写临时文件、fsync、原子发布到全新的编号；POSIX 下同步目录。每个编号仅写一次，不覆盖旧编号；保留最新两代，恢复只选最大编号并验证完整性。运行中不反复修改磁盘 SQLite 文件。关闭时再导出一次完整 .sqlite，交付校验要求检查点解码后的字节与 SQLite 导出完全一致，并与预算、动作数和结束状态交叉核对。

恢复优先读取检查点并验证校验和；它保存 pending 与 committed 状态，沿原 action_id 继续。冻结清单同时包含检查点和 SQLite。运行目录必须整体保留，不应只复制 .sqlite 再称为完整恢复记录。pending 外部模型请求仍按 uncertain 处理，不自动重发。

同时修正了原预算拒绝日志的事务边界：拒绝事件先提交再抛出 BudgetExhausted，避免异常使拒绝记录回滚。拒绝不扣费，但会保留在账本中。

v0.2 在实验冻结前校验已关闭数据库，并将 SQLite 文件哈希纳入冻结清单。之后评分、报告或恢复检查这些哈希，不能把变化后的日志继续当作原实验。

交付数据由修正后的源码完整重跑，具体结果见 validation_report.txt。早期未通过完整性或账本一致性检查的输出没有混入正式结果。修正不改变候选、预算上限、任务规则或评价标签；费用拒绝的日志统计会更准确。

这种快照方式适用于本研究原型，代价是每个事件保存一次数据库图像，较大图的 I/O 和内存占用会增加。它不是多进程共享写入方案，也没有验证所有文件系统或真实断电条件。后续生产化应另行选择并验证可靠的事务存储。

在复核过程中还发现过“最终导出正确，但反复覆盖的检查点停留在较早状态”，因此最终方案使用不可覆盖的递增检查点。交付检查不仅检查文件可读，还检查最新恢复状态、SQLite 导出与实际结果完全一致。
